# Design

## Context

- `apps/api` is Spring Boot 4.2 / Java 21 / PostgreSQL 17. Flyway owns the schema, Hibernate runs with `ddl-auto=validate` (see `add-flyway-migrations`). `V1__init.sql` is an empty baseline and its comment says the first table arrives as `V2`.
- The default profile excludes `DataSourceAutoConfiguration`, so `nx test api` is Docker-free; DB tests use `@Testcontainers(disabledWithoutDocker = true)` (`FlywayMigrationTests`). New tests follow the same pattern.
- Layering is `controller -> service -> repository` (`docs/ARCHITECTURE.md`). Only the `repository` layer is added here; the entity lives next to it.
- There is no users table yet (CC-16).

## Goals / Non-Goals

**Goals:**
- A stored card model that later API, auth and sharing work can use unchanged.
- Repository behaviour proven against real PostgreSQL.

**Non-Goals:**
- Service or controller code, validation messages for clients, a foreign key to users, a many-to-many sharing table.

## Decisions

### D1. English field names, Dutch only in the issue
Code uses `name`, `store`, `cardNumber`, `barcodeType`, `color`, `note`, `createdAt`, `updatedAt`, `ownerId`; columns are snake_case. The rest of the codebase is English. *Alternative: Dutch names from the issue* — rejected for consistency.

### D2. `ownerId` is a plain UUID column, no `@ManyToOne` and no foreign key
Ownership must not be hard-wired to a user entity: sharing will add households and per-person grants next to it, and the users table does not exist yet. A foreign key can be added in CC-16 with its own migration. *Alternative: `@ManyToOne User` now* — rejected, there is no `User` and it would couple card loading to user loading. The cost is that the database cannot yet stop an unknown `ownerId`; CC-19 enforces ownership in the service layer.

### D3. UUID generated by Hibernate (`@GeneratedValue(strategy = GenerationType.UUID)`)
The id is created in the application before insert, so it is known without a round trip and is not guessable like a sequence number. Column type is `uuid`, no database default. *Alternative: `gen_random_uuid()` default* — rejected, it ties id creation to the database for no gain.

### D4. Barcode type as `@Enumerated(EnumType.STRING)` plus a CHECK constraint
Stored by name, so reordering or inserting enum constants cannot corrupt rows (`ORDINAL` would). The CHECK constraint makes the database reject unknown values even when written outside JPA. Adding a type later needs one migration that replaces the constraint. Initial set: `CODE_128`, `EAN_13`, `EAN_8`, `UPC_A`, `QR_CODE`, the common loyalty-card formats; the issue says only "enum". *Alternative: native PostgreSQL enum type* — rejected, harder to alter than a CHECK. *Alternative: a lookup table* — rejected, over-engineered for a fixed list.

### D5. Auditing with `@EnableJpaAuditing` and `Instant`
`@CreatedDate` / `@LastModifiedDate` on `Instant` fields, mapped to `timestamptz`, via `@EntityListeners(AuditingEntityListener.class)`. `createdAt` is `updatable = false`. `@EnableJpaAuditing` goes on its own small `@Configuration` class, not on `ApiApplication`, so it is only active where JPA is (and does not break the DB-free default profile). *Alternative: Hibernate `@CreationTimestamp`* — rejected, the issue asks for `@CreatedDate` as the learning goal and Spring Data auditing is what later `@CreatedBy` would extend.

### D6. Column rules
`name`, `store`, `card_number`, `barcode_type`, `owner_id`, `created_at`, `updated_at` are `NOT NULL`; `color` and `note` are nullable. `color` is free text up to 32 chars and `note` up to 1000; format checks (for example a hex colour) belong to API validation in CC-10, not the table. Index on `owner_id` for the by-owner lookup.

### D7. Repository surface
`LoyaltyCardRepository extends JpaRepository<LoyaltyCard, UUID>` with one derived query, `findAllByOwnerId(UUID)`. Nothing else until an endpoint needs it (YAGNI).

### D8. Tests: `@DataJpaTest` with a Testcontainers PostgreSQL
`@DataJpaTest` with `@AutoConfigureTestDatabase(replace = NONE)` and `@ServiceConnection` on a `PostgreSQLContainer`, so the real Flyway migrations build the schema and the real dialect and constraints are exercised. Needs the `local` profile for the same reason `FlywayMigrationTests` does (the default profile excludes the datasource). Skipped without Docker. *Alternative: H2* — rejected, different dialect, would not test the CHECK constraint or `timestamptz`.

## Risks / Trade-offs

- [No FK on `ownerId`] → documented decision; FK added with the users table (CC-16), tests then cover it.
- [`@EnableJpaAuditing` interaction with the DB-free default profile] → separate config class; `DefaultProfileTests` must keep passing.
- [Barcode type list may be wrong for real cards] → stored by name with a CHECK, so a new type is one small migration.
- [Timestamps compared in tests are flaky] → assert ordering (`updatedAt` after `createdAt`), not exact values.

## Migration Plan

1. Developers with a local database get `V2` applied automatically at the next start; `V1` is not edited.
2. Rollback: revert the commit and run `docker compose down -v` locally; there is no shared database yet.
