# Design

## Context

- The workspace is an Nx 24 monorepo with one Angular project, `apps/web`, configured through an explicit `project.json` (see CC-01). `nx.json` only has the ESLint plugin; there are no JVM plugins.
- The dev machine has JDK 21 (Temurin 21.0.2). There is no global `mvn` or `gradle`.
- The user chose **Maven** for the build tool and **Spring Boot 4.2** over the "Spring Boot 3" in the issue text. Both choices are recorded below.
- Requirements: `specs/api-service/spec.md`.

## Goals / Non-Goals

**Goals:**

- Running the backend feels the same as running the front end: `nx serve|build|test api`.
- A clean checkout plus JDK 21 is enough. The wrapper fetches Maven.
- Keep the setup small and readable, since learning the build tool and Spring Boot startup is the point of this issue.

**Non-Goals:**

- Nx inferring the Maven project graph or dependencies between Java modules. There is only one module.
- Lint/format for Java (Checkstyle, Spotless). This can come later, alongside ArchUnit (CC-34).
- Windows support for the Nx targets. The targets call `./mvnw`. Windows users can run `mvnw.cmd` directly.

## Decisions

### D1. Maven with the Maven Wrapper

Maven 3.10 through `mvnw` (Maven Wrapper 3.3.4, as generated by Initializr), with Maven pinned in `.mvn/wrapper/maven-wrapper.properties`. `spring-boot-starter-parent` 4.2.0 is the parent POM, with `java.version` 21.

- *Why:* Maven is the most common choice in Spring Boot docs and jobs, and its declarative `pom.xml` is easy to learn from. The wrapper removes the need for a global install and pins the version for everyone.
- *Alternatives:* Gradle (Kotlin DSL) is faster and more flexible, but has more concepts to learn up front. The user declined it.

### D2. Nx integration with `nx:run-commands` in `apps/api/project.json`

Each target is a thin wrapper around a Maven command, run with `cwd: apps/api`:

| Target  | Command                         | Notes                                                                                                                                          |
| ------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `serve` | `./mvnw spring-boot:run`        | `continuous: true`, target-level `readyWhen: { url: http://localhost:{env.SERVER_PORT ?? 8080}/api/health }`, so later e2e work (CC-35) can wait for it|
| `build` | `./mvnw -B package -DskipTests` | `outputs: ["{projectRoot}/target"]`, cached; inputs `{projectRoot}/pom.xml`, `{projectRoot}/src/main/**`, `{projectRoot}/.mvn/**`           |
| `test`  | `./mvnw -B test`                | cached; inputs include `{projectRoot}/src/**`                                                                                                  |

`build` skips tests on purpose, so `nx build` and `nx test` stay separate steps, matching how `web` works.

- *Why:* Explicit, with no third-party plugin to keep compatible with Nx 24, and you can read exactly what `nx serve api` runs.
- *Alternatives:* `@nx/maven` (first-party, infers targets from `pom.xml`) has less config but hides the commands, and the user declined it. `@jnxplus/nx-maven` is a third-party plugin, adds generator magic and is one more dependency to keep up to date.

### D3. Spring Boot 4.2 instead of 3.x

- *Why:* 4.2.0 is the current release. The 3.x line (last patch 3.5.16) no longer gets free security patches. Starting on 4.x avoids a migration a few issues from now.
- *Trade-off:* Many tutorials still show 3.x. In 4.x, some starters are split into smaller modules (for example web MVC and test starters) and some test annotations moved packages. Mitigation: generate the skeleton with Spring Initializr for 4.2.0 (D6), so the dependency names are correct, and don't copy them from 3.x examples.

### D4. Health at `/api/health` through the Actuator base path

`application.yml`:

```yaml
server:
  port: 8080
management:
  endpoints:
    web:
      base-path: /api
      exposure:
        include: health
      discovery:
        enabled: false
  endpoint:
    health:
      show-details: never
      probes:
        enabled: false
```

- *Why:* This gives exactly `GET /api/health` → `{"status":"UP"}` with Actuator's standard health endpoint, as the issue asks. Exposing only `health` and never showing details meets the "no other management endpoints / no component details" requirements.
- *Alternatives:* `server.servlet.context-path: /api` would give `/api/actuator/health` and put the prefix on every future controller. That is a bigger decision than this issue needs. A hand-written `HealthController` would duplicate Actuator and drop its aggregation of health indicators.
- *Note:* Actuator now shares the `/api` namespace with application controllers. Future controllers must not use `/api/health`. If more Actuator endpoints are exposed later (CC-36 Observability), move management to its own base path or port at that point.
- `discovery.enabled: false` removes Actuator's links page, which would otherwise answer `GET /api` and claim the `/api` root.
- Boot 4 turns on the liveness/readiness health groups by default, which adds `"groups":[...]` to the body. `probes.enabled: false` keeps the body at exactly `{"status":"UP"}`. Turn it back on when deploying to a platform that uses probes (CC-37).
- Actuator answers with content type `application/vnd.spring-boot.actuator.v3+json`. The spec allows a JSON vendor type.

### D5. Package-by-layer under one base package

Group `com.ccards`, artifact `api`, base package `com.ccards.api`, main class `com.ccards.api.ApiApplication`. Sub-packages:

- `controller` – HTTP layer (`@RestController`). No business logic.
- `service` – business logic and transactions.
- `repository` – data access (Spring Data, from CC-08).

Each package gets a `package-info.java` describing its role, so the empty layers are in git and document themselves. The README repeats the layout and the rule "controller → service → repository, never the other way round". ArchUnit (CC-34) will enforce it later.

- *Alternatives:* Package-by-feature (`card/`, `user/`) scales better, but the issue asks for the classic layers as a learning aid. We can revisit this once there are several features.

### D6. Generate the skeleton with Spring Initializr

Download the project zip from `start.spring.io` (Maven, Java 21, Boot 4.2.0, dependencies: web + actuator, group/artifact/package as in D5), unzip it into `apps/api`, then trim it: remove `HELP.md`, replace `application.properties` with `application.yml`, add `project.json`.

- *Why:* This gives a correct `pom.xml`, the Maven Wrapper scripts and the right Boot 4 starter names without a global Maven. Doing the same by hand is error-prone.
- The download happens during apply and needs the user's OK at that time.

### D7. Test strategy

One `@SpringBootTest(webEnvironment = RANDOM_PORT)` test that sends an HTTP `GET /api/health` and asserts status 200 and `status == "UP"`. A second assertion checks that a non-exposed management path (for example `/api/env`) returns 404. The random port keeps tests from clashing with a running `nx serve api`. Use the test HTTP client that Boot 4 provides (for example `RestTestClient`, or `TestRestTemplate` if it is still offered), whichever the Initializr test starter brings in.

## Risks / Trade-offs

- [The first `nx serve|test api` is slow because it downloads Maven and dependencies into `~/.m2`] → Document this in the README. Later runs are offline-fast.
- [Nx cache replays a stale `build` if inputs are too narrow] → Inputs cover `pom.xml`, `.mvn/` and `src/main/`. Maven's own incremental build in `target/` stays the source of truth.
- [The `run-commands` option `readyWhen` (a log-line match) marks the task *finished* and stops the server] → Use Nx's target-level `readyWhen.url` on the health endpoint instead. It only signals readiness to dependents.
- [`./mvnw` needs the execute bit] → Commit `mvnw` with mode 755 (`git update-index --chmod=+x`).
- [Nx 24 reports a `continuous` target that exits with an error as "Successfully ran" (exit 0)] → This is Nx behavior, not ours (the same command without `continuous` fails correctly). The Spring error "Port 8080 was already in use" is still printed. We keep `continuous: true` so CC-35 can depend on `serve`, and the README warns to read the log.
- [Port 8080 is taken by another local tool] → The spec makes the failure explicit. Developers can override it with `SERVER_PORT` / `--server.port` without a code change.
- [Boot 4 vs 3 material mismatch while learning] → Covered under D3.

## Migration Plan

Additive only. There is no runtime to migrate. Rollback means deleting `apps/api` and reverting the README and `.gitignore` edits.
